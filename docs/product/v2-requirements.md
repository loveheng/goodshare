### 1.1a 收敛拍板记录（2026-10-09，用户提出、AI 对账确认）

评估结论：v2 原稿存在**战略意图（§1.3 MCP 优先）与功能设计（R1–R5）的割裂**——四处把云端全功能 Agent 体验塞进移动端 1.5B 小模型的过度设计。四项收敛：

1. **砍 R4**：编辑器回归纯文本/块编辑手感。错别字校对/文风切换交桌面或云端；Diff 高亮/CAS 还原逻辑全部不上。注：`ai_revisions` 写回快照与乐观锁是 **AI 写回可逆**（ai-writeback-revert.md，2026-10-04 已落地）的地基，非 R4 专属，保留。
2. **砍 R3**：截图价值=OCR 文本入库可搜可复制（基线已达成）。发票/名片结构化若真有需求，桌面 MCP 抓 OCR 文本用大模型清洗，端侧零投入。
3. **收窄 R1**：chatlog 输入源本就有限（§3.1 自认「来源有限」）且 OCR 碎片动辄数千字超出 4096 ctx——端侧 1.5B 理不清长聊天记录的逻辑，整理产出不可信；超长分块/Map-Reduce 基建不为此铺设（Phase 2/4 仅在向量检索需要时另行评估）。**已落码的 chatlog 分支删除**（taskParseChatlog 认领+降噪改写，约 40 行）；taskActionFor(chatlog) 回归 null（占位消化）。
4. **R5 除名**：温控方向对但「真机逐 ROM 验证」投入产出比陷阱——ROM 温控上报黑盒不值得死磕；电量门控+超时熔断+串行队列已闭环。

**二次收敛（2026-10-09 同日晚，用户四点精简再拍板）**：

5. **D3 一刀切改头部截断**：超 3000 字回退占位会让 70%+ 真实长文（公众号/技术长文 3000-8000 字）摘要哑火——改**头部 1500 字符截断直出**（核心论点集中前 2-3 段，极低成本覆盖 80% 场景），不搞分块。
6. **链式任务改串联单任务**：跨任务链+产出特征闸+轮内单链闸=分布式调度（Airflow 思维）硬塞本地 SQLite 队列——改 Composite Pipeline：抓取→原地调 LLM→一次落库，代码减半、死循环隐患**物理归零**。
7. **开关收敛**：自动摘要开关删（下载 1.5GB 模型本身即强意图，模型在位即生效）；打码开关删（核心隐私防御硬编码，无人会主动要求保留明文卡号）。
8. **配套收敛**：仅保留配套①④（均已完成）；配套② 预置链彻底删除、配套③ 图文修复延后出 V2。

收敛后本期范围 = **R1(URL 抓取+摘要) + R2(打码)**。R2 已收官；R1 的抓取半环已落地，**摘要半环随 2026-10-14 ai-app-split M2 迁至宿主 App**——URL 分享照常抓取落库，TL;DR/标签由宿主经 `summarize_item`/`extract_tags` 认领完成；**宿主闭环已于 2026-10-15 跑通**（ai-app-split 账本），V2 本期实际收官。

多源健康数据接入与 `health_record.v1` 已砍除（2026-10-15，用户拍板「发展方向已变、放弃不做」，见 context/decisions.md），本文不再覆盖。

### 1.3 范围对齐、加工主体与实施排序（2026-10-02 评估+拍板）

内容来源重心已从网页转向 **app 分享**，且**文本大头在媒体提取**：音视频转写（1h ≈ 45KB）> 图片 OCR > 网页抓取（收益下降中，维持现状不投入）> 人手写便签（最小）。OCR/转写文本已入库可搜（human_md），加工链路已全通但全手动。

**加工主体拍板（2026-10-02）**：人类端只做**当前需要**的即时操作（读、搜、单条处理、人工修订）；**繁重加工（转写/OCR/摘要/打标/结构化）交给桌面 AI 客户端经 MCP 驱动**——Human-AI 对称性（`../architecture/human-ai-parity.md`）的产品化推论：AI 是「头」，UI 是按需入口。

> 范围边界（2026-10-02 拍板）：MCP 客户端分域授权（按客户端发 token + 工具/数据/内容形态三维 scope，processed 档与 R2 打码层协同）经评估成立但**划入 V3**——V2 维持单 token + Vault 隔离的信任模型，先把 MCP 加工链路走通。SSOT：PRD §9 V3 行。

## 2. 技术路线（现行口径，2026-10-14 M2 后）

**端侧 LLM 路线已终结**：2026-09-28 曾拍板「LiteRT-LM + Qwen2.5-1.5B 下载」路线（Android）/「FoundationModels 系统模型」（iOS），2026-10-14 ai-app-split M2 将整套引擎**迁出本仓**。现行路线：

- **goodshare（本仓）**：不持有任何大模型。保留 ML Kit 全族（OCR/分类/条码/实体/翻译）、Sherpa 端侧转写、非模型任务（URL 抓取/文档归一化/主色提取）；LLM 类任务（`llm_summarize`/`llm_tags`/`block_summarize`/`template_apply`）入队后滞留 pending，由 AI 宿主 App 经 `claim_ai_task` 认领、`apply_ai_result` 回写（占位守卫保证本机管线不吞远程任务）。
- **AI 宿主 App（goodhub，独立仓）**：自有引擎（端侧 LiteRT-LM 或云端 LLM，BYOK），模型目录/下载管理/推理桥细节随迁，SSOT 在宿主仓。
- 接缝契约（三工具 + 乐观锁 + 打码同出口 + 心跳回收）以 `../design/ai-app-split.md` 为唯一事实源，本文不重复。

## 3. R1 · 摄入自动双态重构管线

### 3.1 现状与缺口（已落地）

摄入链路按类型自动入队（`Repository.taskActionFor`）：url → 抓取任务（`summarize_url` 常量 2026-10-09 起不再作为独立动作入队，历史任务行兼容）。chatlog 经 2026-10-09 收敛拍板（§1.1a）**不再入队**（`taskActionFor` 回归 null，占位消化）。

- **url**：`OcrReconstructor` 自动离线抓取网页正文写入 `human_md`（保结构 Markdown）+ OG 元数据富化——事实源。
- **chatlog**：~~LLM 议题整理~~已砍——1.5B 理不清长 OCR 碎片的逻辑，整理产出不可信。

### 3.2 需求（抓取半环已落地；摘要半环 2026-10-14 迁出宿主）

**原设计（已退役）**：Composite Pipeline——`OcrReconstructor` 抓取正文后**原地**调 `LlmReconstructor.summarizeUrlHead`（组装点回调注入）产 TL;DR+标签，同一任务一次落库。**2026-10-14 ai-app-split M2 拆除端侧 LLM 后，`summarizeHead` 注入点改 null**（main.dart 装配移除），走既有「模型不在位静默跳过」路径，零新逻辑。

**现行口径**：

- **URL 摄入**：抓取正文照常落库（含 OG 富化）；无自动摘要、无噪音 note；URL 不再自动入队任何 LLM 任务。
- **摘要/打标**：由 AI 宿主 App 经 MCP `summarize_item`（入队 `llm_summarize` → claim → apply 回写 `summary_md`）或 `extract_tags` 手动触发；产出经 `get_item`（`summary`/`summary_stale` 字段）可读，与原文并列不覆盖。
- **头部 1500 截断、模型在位静默跳过、无链无闸无开关**等原二次收敛结论随引擎迁出失效（截断/超限处理归宿主按自身 ctx 决定，goodshare 传全文）。
- taskParseChatlog / taskSummarizeUrl 常量保留（历史任务行兼容，占位消化）。

## 4. R2 · 隐私打码层（已落码）

AI 产出**必经本地规则层**（端侧，不外传），已按 D1 拍板挂**通用出口**：

- 规则：18 位身份证号（regex + GB 11643 校验位）、银行卡号（13–19 位 + Luhn 校验）→ 默认 `****` 打码（长编号边界守卫防误伤）；**硬编码恒开**（二次收敛拍板：核心隐私防御不做开关）。
- 作用面：`_applyAiResult` 出口处 `human_md` 与 `machine_json` 同步打码，**覆盖所有 AI 写路径含占位回退**；`raw_content` 保留明文。
- 落点：`lib/ai/privacy_mask.dart` 纯函数 + `ItemActionHandler.isMaskEnabled` 注入（UI/MCP/管线换入口也绕不过）。

## 5. R3 · ~~通用截图解析~~（砍除，2026-10-09 §1.1a）

**整条砍除，未动工零返工**。理由：截图价值 = OCR 文本入库可搜可复制（基线已达成）；端侧 1.5B 零样本领域分类 + 严格 Schema 结构化的字段填充率与格式遵从度不可信，验证器/容错/降级投入为极低频场景建重基建。发票/名片结构化属**重活**——归桌面 AI 客户端经 MCP 抓 OCR 文本批处理（§1.3 加工主体拍板的直接推论）。`invoice.v1`/`contact.v1`/`event.v1` validator 登记保留（Schema 定义零成本，供桌面端/未来复用）。

## 6. R4 · ~~便签编辑器 AI 增强~~（砍除，2026-10-09 §1.1a）

**整条砍除，未动工零返工**。理由：① 1.5B q8 的中文校对必然海量误报/漏报，高亮打断记录心流；文风切换产出不可信、用户不敢采纳；② 为低频伪需求铺 Diff 高亮 + 版本快照还原 + CAS 冲突仲裁，是给本地单人文档做协同级工程——过度工程。编辑器回归纯文本/块编辑手感；校对/改写需求交桌面或云端。注：`ai_revisions` 写回快照与乐观锁是 **AI 写回可逆**（ai-writeback-revert.md）的地基，非 R4 专属，保留。

## 7. R5 · ~~温控节流~~（除名，2026-10-09 §1.1a）

**从需求表除名**。防过热已由既有三件套 100% 覆盖：电量门控（`canProcess`）+ 单任务超时熔断（60s~600s 分档强杀）+ 队列严格单线程串行。「真机逐 ROM 验证 ThermalStatus 上报」是 ROM 黑盒里的精力陷阱，不做。

## 8. MCP 与 Schema 增量（收敛后）

- **MCP 零新增工具**：模型升级后的重放由既有 `reprocess_item` 承担；所有产出经 `get_item` 可读、失败经 `last_task.note` 可观测（Human-AI 对称性既有规则）。
- **重活归 MCP**（收敛拍板的正向落点）：截图结构化、长文校对/改写等端侧砍除的能力，桌面 AI 客户端经既有工具族（`get_item` 取 OCR/正文 → 云端大模型加工 → `add_item`/`update_item` 回写）即可完成，app 零新增。
- **Schema**：`invoice.v1` / `contact.v1` / `event.v1` validator 登记保留（零成本，供桌面端复用）；`machine_json` 取值本期无扩展，**无需新建表**。
